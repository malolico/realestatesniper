# I. Definición constitucional del Loop

## I.1 ¿Qué es un Loop?

Un **Loop** es una **entidad permanente de supervisión y perfeccionamiento** en Factory 2.0 con las siguientes propiedades:

| Propiedad | Definición |
|-----------|------------|
| **Identidad** | Nombre canónico, versión y ámbito de supervisión declarados |
| **Misión** | Maximizar calidad, frescura, suficiencia y coherencia del conocimiento en su ámbito |
| **Supervisión** | Conjunto explícito de motores MOT-XX-NN y/o capacidades CAP-XX |
| **Activación** | Condiciones epistémicas, temporales o de evento que lo ponen en marcha |
| **Finalización** | Condiciones de reposo, handoff o cierre de investigación |
| **Presupuesto** | Límites de coste, profundidad y tiempo de perfeccionamiento |
| **Auditabilidad** | Registro de decisiones de re-ejecución, cambio de estrategia y agotamiento |

Un Loop **no es** un motor, un producto, un tier, una decisión comercial ni un agente de publicación.

## I.2 Misión del Loop

> **Gobernar cuándo, por qué y con qué estrategia se re-ejecutan motores para elevar la calidad epistémica del conocimiento — sin producir conocimiento primario ni redefinir misiones motor.**

La misión incluye:

- Evaluar si el conocimiento actual cumple umbrales de calidad, frescura y suficiencia
- Decidir re-ejecución de motores con criterios explícitos — no por fallo técnico ciego
- Orquestar secuencias de perfeccionamiento dentro de su ámbito
- Cambiar de estrategia cuando una línea de investigación deja de ser rentable
- Declarar agotada una línea cuando el beneficio marginal es inferior al coste
- Solicitar cooperación a otros Loops o derivar a Enjambre cuando la convergencia excede su ámbito
- Respetar prioridades constitucionales y presupuesto epistémico
- Registrar toda decisión para auditoría y observabilidad

## I.3 Lo que un Loop NUNCA es

| Anti-patrón | Por qué es ilegítimo |
|-------------|----------------------|
| **Reintento técnico** | Reintento = misma estrategia tras error infra; Loop evalúa calidad epistémica |
| **Cron job ciego** | Ejecutar motor por calendario sin evaluar beneficio marginal |
| **Motor disfrazado** | Loop no produce elementos DDI primarios |
| **Decisor Diamond** | Decision-Diamond es acto soberano aguas abajo |
| **Publicador** | Producto y Projection gobiernan exposición |
| **Asignador de tier** | `access_tier` es tabú en toda Fase II |
| **Expansor del DDI** | Ley de no expansión |
| **Override de evidencia** | MOT-EVD-01/02 prevalecen — Loop escala, no promedia |
| **Bypass de compliance** | MOT-CMP-01 veto soberano |
| **Motor no catalogado** | Solo MOT-XX-NN del OMC |
| **Enjambre** | Convergencia multi-motor compleja es dominio Enjambre — Loop deriva, no sustituye |
| **IA autónoma** | Asistencia futura obedece gobernanza — no sustituye Loop |

## I.4 Lo que un Loop NUNCA debe hacer

| Prohibición | Razón constitucional |
|-------------|----------------------|
| **Redefinir misión de motor** | LMC-19 / MMA-07 |
| **Ejecutar motor no catalogado** | LMC-03 / OMC-01 |
| **Inventar hechos para cerrar gap** | MMA-02 / LS-11 |
| **Promediar conflictos probatorios** | LS-09 / MOT-EVD-02 |
| **Forzar C1–C2 sin evidencia** | DDI / Dominio 42 |
| **Re-ejecutar sin criterio declarado** | MLA gobernanza |
| **Ignorar presupuesto epistémico** | Coste-beneficio obligatorio |
| **Ocultar agotamiento de línea** | Gap declarado > dato inventado |
| **Saltar capas de dependencia** | DEP-01..08 del OMC |
| **Sustituir MOT-SYN / MOT-EXE** | CAP-21 / CAP-24 soberanos |

# II. Filosofía de los Loops

## II.1 Principios fundacionales

| Principio | Enunciado |
|-----------|-----------|
| **P-01 — Calidad sobre velocidad** | Mejor conocimiento calibrado que cobertura nominal vacía |
| **P-02 — Permanencia sobre episodio** | El Loop existe mientras Factory exista en su ámbito — no nace con un deal y muere con un error |
| **P-03 — Criterio sobre reintento** | Re-ejecutar motor exige justificación epistémica medible |
| **P-04 — Beneficio marginal** | Cada ciclo debe demostrar valor esperado de información |
| **P-05 — Agotamiento honesto** | Declarar «no se puede mejorar más con recursos razonables» es acto de virtud |
| **P-06 — Soberanía motor** | Loop supervisa cuándo — Motor gobierna qué produce |
| **P-07 — Evidencia primero** | Sin suficiencia probatoria no hay escalado a síntesis |
| **P-08 — Compliance inviolable** | Ninguna optimización de calidad bypass MOT-CMP-01 |
| **P-09 — Trazabilidad total** | Toda decisión de Loop es auditable |
| **P-10 — Cooperación declarada** | Ayuda entre Loops y derivación a Enjambre son actos explícitos |

## II.2 Loop vs Reintento vs Motor vs Enjambre

```text
MOTOR     → Produce conocimiento (QUÉ)
LOOP      → Perfecciona calidad del conocimiento (CUÁNDO / POR QUÉ / HASTA CUÁNDO)
ENJAMBRE  → Coordina convergencia multi-motor compleja (CÓMO conjunto) — futuro
REINTENTO → Recuperación técnica misma operación — FUERA de MLA
```

| Dimensión | Motor | Loop | Reintento técnico |
|-----------|-------|------|-------------------|
| **Naturaleza** | Productor | Supervisor permanente | Recuperador puntual |
| **Disparador** | Loop, evento, manual | Degradación calidad, gap, frescura | Timeout, 5xx, red |
| **Criterio éxito** | Knowledge delta válido | Mejora medible E/C/cobertura | Operación completada |
| **Fin** | Manifest de ejecución | Reposo, handoff o agotamiento | Ack o dead-letter |
| **Presupuesto** | Coste por run | Coste-beneficio acumulado | Límite técnico fijo |
| **Estrategia** | Fija por misión | Puede cambiar entre ciclos | Idéntica |

## II.3 Epistemología del perfeccionamiento

El Loop opera sobre **estado epistémico** del conocimiento — no sobre estado técnico de jobs:

| Señal epistémica | Ejemplo | Respuesta Loop típica |
|------------------|---------|------------------------|
| **Degradación C** | Payoff >90 días → C3 | Re-ejecutar MOT-FIN-02 |
| **Gap Obl.** | Sin deed vigente | Activar MOT-OCR-01 con estrategia documental |
| **Conflicto E** | Assessor vs recorder parcel | Escalar a Loop evidencia / MOT-EVD-02 |
| **Frescura vencida** | FEMA map revision | Re-ejecutar MOT-HAZ-01 |
| **Insuficiencia** | <3 comps | Loop mercado amplía radio MOT-MKT-02 |
| **Blocker activo** | Lis pendens nuevo | Loop distress re-ejecuta MOT-JUD-01 |
| **Convergencia débil** | Una sola señal MOT | Loop motivación solicita segunda fuente |

# III. Relaciones constitucionales

## III.1 Cadena soberana con Loops

```text
FUENTES (DSO)
        ↓
MOTORES (OMC — 52)  ←—— supervisados por ——→  LOOPS (MLA)
        ↓                                        ↓
CONOCIMIENTO (estado epistémico)          decisiones de perfeccionamiento
        ↓
EVIDENCIAS (MOT-EVD-01/02)
        ↓
SÍNTESIS (MOT-SYN) ←—— Loop Readiness supervisa
        ↓
DECISION → PROJECTION → PRODUCTO
```

## III.2 Loop × Motor (OMC)

| Relación | Regla |
|----------|-------|
| **Supervisión** | Todo Loop declara motores supervisados — lista cerrada OMC |
| **Re-ejecución** | Loop ordena re-run; Motor ejecuta su misión sin alteración |
| **Prohibición** | Loop no modifica I/O contractual del Motor |
| **Dependencias** | Loop respeta DEP-01..08 y orden capas 1→6 |
| **Hub motors** | MOT-EVD-01, MOT-CHR-01, MOT-CMP-01 tienen Loops transversales dedicados |

## III.3 Loop × Capacidad (FCC)

| Relación | Regla |
|----------|-------|
| **Alineación** | Todo Loop declara CAP-XX primario de supervisión |
| **Cobertura** | 26 capacidades deben tener ≥1 Loop supervisor en catálogo futuro |
| **No expansión** | Loop no crea capacidad — obedece FCC |
| **Capa** | Loops de capa N no finalizan perfeccionamiento de capa N+1 sin handoff |

## III.4 Loop × Sources (DSO)

| Relación | Regla |
|----------|-------|
| **Frescura** | Loops aplican reglas de actualización definidas en DSO |
| **Fuente vencida** | LS-10 — Loop activa re-ejecución, no certifica stale |
| **Nueva fuente** | Cambio fuente = enmienda DSO — no decisión Loop ad hoc |
| **Prohibidas** | Loop no autoriza fuente prohibida para «completar» gap |

## III.5 Loop × Evidencia (CAP-20)

| Relación | Regla |
|----------|-------|
| **Árbitro** | MOT-EVD-02 resuelve conflictos — Loop escala, no decide mérito |
| **Suficiencia** | Loop Readiness no declara go sin sufficiency MOT-EVD-01 |
| **Registro** | Toda re-ejecución ordenada por Loop genera entrada audit trail |

## IV.1 Por misión de supervisión

| Tipo | Código | Pregunta que responde |
|------|--------|----------------------|

# VI. Ciclo de vida del Loop

```text
DISEÑO → APROBACIÓN → REGISTRO → ACTIVO ⇄ CICLO ⇄ REPOSO → DEPRECACIÓN → RETIRADO
                              ↑              ↓
                         AUDITORÍA      AGOTAMIENTO / HANDOFF
```

| Fase | Descripción | Gate |
|------|-------------|------|
| **Diseño** | Misión, motores, activadores, presupuesto | Alineación MLA + OMC |
| **Aprobación** | Inclusión en Official Loop Catalog | Architecture Board |
| **Registro** | Versión 1.0.0 publicada | MLA compliance |
| **Activo** | Supervisión en producción | Métricas dentro SLA |
| **Ciclo** | Evaluar → decidir → re-ejecutar o escalar → medir | Registro audit trail |
| **Reposo** | Objetivo cumplido o presupuesto agotado | Finalizador declarado |
| **Deprecación** | Reemplazo por Loop sucesor | Dual-run transición |
| **Retirado** | No nuevas supervisiones | Histórico decisiones preservado |

## VI.1 Estados operativos de un ciclo

| Estado | Significado |
|--------|-------------|
| **DORMANT** | Activo epistémicamente suficiente — Loop observa sin actuar |
| **EVALUATING** | Midiendo calidad, frescura, gaps |
| **PERFECTING** | Re-ejecutando motores bajo criterio |
| **STRATEGY_SHIFT** | Cambió táctica de perfeccionamiento |
| **COOPERATING** | Solicitó ayuda a otro Loop |
| **ESCALATING** | Derivó a Enjambre (conceptual) |
| **EXHAUSTED** | Línea agotada — gap declarado permanece |
| **RESTING** | Finalizador alcanzado — espera próximo activador |

## VI.2 Ciclo canónico de perfeccionamiento

```text
    ┌─────────────┐
    │  ACTIVADOR  │
    └──────┬──────┘
           ▼
    ┌─────────────┐     no mejora      ┌──────────────┐
```

# IX. Criterios de re-ejecución de motores

## IX.1 Marco general

El Loop **nunca** re-ejecuta motor por defecto. Re-ejecución exige **triple condición**:

1. **Señal** — activador epistémico válido  
2. **Beneficio** — mejora esperada ≥ umbral declarado  
3. **Elegibilidad** — dependencias hard satisfechas; compliance clear  

## IX.2 Criterios por señal epistémica

| Señal | Criterio re-ejecución | Motor típico |
|-------|----------------------|--------------|
| **Frescura** | age(data) > SLA_DSO(domain) | MOT capa correspondiente |
| **Degradación C** | C_new < C_min(domain) | Productor primario dominio |
| **Gap Obl.** | gap.status = OPEN ∧ benefit > cost | MOT-ACQ/VER del dominio |
| **Conflicto** | conflict.unresolved = true | MOT-VER o MOT-EVD-02 |
| **Nuevo evento** | event.material = true ∧ ¬incorporated | MOT-SIG / MOT-CHR |
| **Dependencia** | upstream.version ≠ consumed.version | MOT downstream hard-dep |
| **Insuficiencia** | sufficiency = FAIL | MOT productor + MOT-EVD-01 |

## IX.3 Reglas de re-ejecución

| Regla | Enunciado |
|-------|-----------|
| **RE-01** | Re-ejecución registra **razón epistémica** — no solo timestamp |
| **RE-02** | Mismo motor + misma estrategia + mismo input → **máximo N runs** por ventana |
| **RE-03** | Tras N sin mejora Δ → **cambio de estrategia** o agotamiento |
| **RE-04** | Re-ejecución capa 6 prohibida si MOT-EVD-01 sufficiency = FAIL |
| **RE-05** | Re-ejecución MOT clase C tiene **prioridad** sobre clase S en presupuesto |
| **RE-06** | Loop no re-ejecuta motor si MOT-CMP-01 = BLOCK |

## IX.4 Mejora mínima exigible (Δ)

| Dimensión | Δ mínimo para continuar ciclo |
|-----------|------------------------------|
| **Confianza C** | +1 nivel C, o C5→C4 no aplica — solo ascenso hacia C1–C2 |
| **Evidencia E** | +1 nivel E, o nueva evidencia E4 |
| **Cobertura** | +≥5% elementos Obl. ámbito, o cierre gap específico |
| **Frescura** | age < SLA post-run |
| **Blocker** | Resolución blocker o downgrade documentado |

Si Δ < mínimo tras run → cuenta hacia agotamiento (RE-03).

# XI. Agotamiento de línea de investigación

## XI.1 Definición

**Agotamiento** es el acto soberano del Loop de declarar que **no existe beneficio marginal razonable** en continuar perfeccionando un objetivo epistémico con los recursos y estrategias autorizadas.

Agotamiento **no es fallo** — es cumplimiento de P-05.

## XI.2 Condiciones de agotamiento

| Condición | Umbral conceptual |
|-----------|-------------------|
| **Presupuesto** | cost_accumulated ≥ budget_epistemic |
| **Rendimientos decrecientes** | Δ último ciclo < Δ_min por M ciclos consecutivos |
| **Fuentes agotadas** | Todas las familias DSO aplicables ejecutadas |
| **Estrategias agotadas** | STR-1..STR-7 aplicadas sin Δ |
| **Irresolubilidad** | MOT-EVD-02 declara irresoluble |
| **Blocker permanente** | Blocker sin vía de resolución factory |

## XI.3 Efectos del agotamiento

| Efecto | Regla |
|--------|-------|
| **Gap** | Permanece en known gaps — nunca inventado |
| **C** | No se eleva artificialmente |
| **Estado Loop** | EXHAUSTED → RESTING |
| **Re-apertura** | Solo por ACT-V evento material nuevo |
| **Síntesis** | MOT-SYN registra agotamiento como known unknown |
| **Decision** | Blocker puede impedir go — agotamiento no fuerza go |

## XI.4 Agotamiento prohibido

| Situación | Por qué |
|-----------|---------|
| Blocker C1 sin intentar STR-1..STR-5 | Negligencia constitucional |
| Gap Obl. con fuente disponible no intentada | Cobertura nominal falsa |
| Agotamiento sin audit trail | Gobernanza falsa |
| Agotamiento para cumplir SLA nominal | Viola P-01 |

**Regla ESC-S:** Loop **deriva** — no ejecuta Enjambre. Enjambre obedece Swarms Architecture (documento 15). Este documento **no define** enjambres concretos.

# XIII. Cooperación entre Loops

## XIII.1 Patrones de cooperación

| Patrón | Descripción |
|--------|-------------|
| **Pipeline** | LOOP-FND → LOOP-LEG → LOOP-DST → … secuencial capas |
| **Parallel** | Loops misma capa supervisan motores independientes |
| **Challenge** | LOOP-QLT disputa suficiencia de LOOP-SUP |
| **Handoff** | LOOP-GAP cede a LOOP-EVD tras conflicto |
| **Watch** | LOOP-FRS observa sin actuar — alimenta ACT-T |

## XIII.2 Reglas de cooperación

1. Cooperación **declarada** en ficha Loop — no emergente.  
2. Loop receptor **acepta o rechaza** handoff con causa.  
3. Dos Loops **no supervisan** re-ejecución del mismo motor simultáneamente — lock conceptual.  
4. Loop transversal XVR **no anula** misión Loop de capa.  
5. Cooperación **no fusiona** Loops en super-Loop ad hoc.

## XIII.3 Orden de precedencia entre Loops
